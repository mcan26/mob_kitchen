1 · Mobile Context & OS Lifecycle Resilience (EI-1057 Theory 1–2 & Lab 1) Offline-First Core

Why Cloud-Only Kitchen Apps Fail on Mobile Devices

Three physical kitchen & supermarket constraints solved through clean mobile systems engineering:

1. Supermarket Dead Zones (0 bps)

  • Problem: Basement supermarkets lose LTE/5G signal right when users need their grocery list.
  • Solution: Reactive relational SQLite (Drift) in app_database.dart (Recipes, Ingredients, ShoppingListItems).
  • Impact: Deterministic ingredient aggregation (SmartShoppingAggregator) with zero network latency.

2. OS Background Doze & Lock

  • Problem: Android/iOS throttles Timer.periodic when the phone screen locks or backgrounds.
  • Solution: Wall-clock targetEndTime timestamp + WidgetsBindingObserver (AppLifecycleState.resumed).
  • Impact: Zero timer drift upon unlock + hands-free display wake via WakelockPlus.

3. Multi-Device Kitchen Latency

  • Problem: Two people shopping or cooking together need instant state sync without cloud logins.
  • Solution: Local ad-hoc UDP :41234 discovery + WebSocket :8765 P2P sync.
  • Impact: < 10 ms LAN latency across Android & iOS devices.

3 · Native Mobile OS Network APIs (EI-1057 Theory 5 & Lab 5) Kotlin + Swift Bridge

Android Kotlin & iOS Swift Radio Diagnostics Bridge

Bridging OS-level hardware radio telemetry into Flutter via MethodChannel("com.mobkitchen/native_network"):

🤖 Android Native (MainActivity.kt)

  • ConnectivityManager + NetworkCapabilities: Detects active transport (TRANSPORT_WIFI, TRANSPORT_CELLULAR, TRANSPORT_ETHERNET) and Android 10+ caps.signalStrength.
  • WifiManager.connectionInfo: Reads physical RSSI (dBm), Link Speed (Mbps), and Frequency (MHz) (classifying ≥ 4900 MHz as 5 GHz vs. 2.4 GHz).
  • LinkProperties & NetworkInterface: Prioritizes private RFC-1918 LAN IPv4 on wlan0 / ap0 (192.168.x.x).
  • BluetoothManager.adapter: Reports hardware BLE radio state (ON / OFF).

🔒 Android 12–15 Security & iOS getifaddrs

  • AndroidManifest.xml (API 31–36):
    NEARBY_WIFI_DEVICES & BLUETOOTH_SCAN with android:usesPermissionFlags="neverForLocation" — discovers BLE & Wi-Fi peers without harvesting user GPS location.
  • CHANGE_WIFI_MULTICAST_STATE + WifiManager.MulticastLock: Acquires simmerlink_udp_manet_lock in MainActivity.kt so Android Wi-Fi chipsets do not filter incoming UDP Broadcast (:41234) packets.
  • iOS Native (AppDelegate.swift): Inspects BSD POSIX getifaddrs on interface en0 (AF_INET) to resolve Wi-Fi IPv4 natively on iPhone & iOS Simulator.

4 · MANET Discovery vs. Reliable P2P Sync (EI-1057 Lab 3 & Lab 4) UDP :41234 + WS :8765

Why UDP Broadcast (:41234) + Full-Duplex WebSocket (:8765)?

Two-phase local peer-to-peer protocol in lib/features/wireless/data/lan_sync_engine.dart:

Phase 1 · Connectionless Discovery

UDP Broadcast (RawDatagramSocket :41234)

  • Binds to 0.0.0.0:41234 with reuseAddress = true and broadcastEnabled = true.
  • Broadcasts every 4 seconds to 255.255.255.255:41234 + directed /24 subnet broadcast (192.168.x.255):
    {"type":"simmer_beacon","ip":"192.168.1.42","port":8765,"room":"SIMMER-2026"}
  • Why not TCP scan? Scanning 254 IPs via TCP requires 254 3-way handshakes and triggers OS firewall rate limits; 1 UDP datagram reaches the subnet in < 2 ms.
Phase 2 · Reliable Full-Duplex Sync

TCP HTTP + WebSocket (HttpServer :8765)

  • Upgrades discovered peers automatically to ws://<peer-ip>:8765/ws (with POST /sync HTTP fallback).
  • Echo-Storm Prevention (_pkt_id): Every frame carries a unique ID checked against a 256-entry _seenPacketIds ring buffer so mutually connected phones never loop packets infinitely.
  • Socket Reuse (_outboundSocketsByEndpoint): Reuses open WebSockets across periodic 4-second UDP beacons.
